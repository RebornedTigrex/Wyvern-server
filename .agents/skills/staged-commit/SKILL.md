# staged-commit

Skill для постановки изменений в git в виде серии маленьких, понятных коммитов,
сгруппированных по смысловым единицам.

## Алгоритм работы

### 1. Собери картину изменений

Запусти `git status` и `git diff --stat`, чтобы увидеть все изменённые и новые файлы.

### 2. Определи смысловые группы

Группируй файлы по одному из принципов (выбирай исходя из природы изменений):

**По слою архитектуры** (для фич с несколькими модулями):
- `deps` — обновления подмодулей, lock-файлов, vcpkg/pip зависимостей
- `build` — CMakeLists.txt, build-скрипты, пресеты
- `<feature>/transport` (или `low-level`) — сетевой/IO уровень
- `<feature>/crypto` — шифрование, ключи, сессии
- `<feature>/db` — хранилище, репозитории, схема
- `<feature>/app` (или `business`) — бизнес-логика, сценарии, команды
- `<feature>/platform` — точка входа, регистрация модулей

**По модулю/компоненту** (для изменений в нескольких независимых модулях):
- один коммит = один модуль или одна фича

**По типу изменения** (для hotfix/refactor):
- один коммит = один тип (bugfix / refactor / test / docs)

**Порядок коммитов**: зависимости всегда раньше зависимых. Если `crypto` зависит от `transport`, коммить `transport` первым.

### 3. Предложи план пользователю

Перечисли предложенные группы в виде нумерованного списка:
```
1. deps:       EXTERNALS/some_lib (submodule update)
2. transport:  src/transport/UdpModule.h/.cpp
3. crypto:     src/crypto/CryptoModule.h/.cpp
4. app:        src/app/MessengerModule.h/.cpp
5. build:      CMakeLists.txt
```

Спроси подтверждение, если разбивка неочевидна. Если пользователь не возражает — выполняй.

### 4. Коммить группу за группой

Для каждой группы:
1. `git add <конкретные файлы группы>` — только файлы этой группы, не `git add .`
2. `git commit -m "<сообщение>"` с форматом ниже

## Формат коммит-сообщения

Используй стандарт из правил проекта (если есть `AGENTS.md` или аналог, прочитай его).
Если нет — используй этот шаблон:

```
<scope>: <краткий заголовок>

Что сделано:
- пункт 1
- пункт 2

Новые точки взаимодействия (только новые в этом коммите):
- ИмяСущности - Файл/Модуль - Как используется

Зачем это сделано:
1-2 предложения: какую проблему решает, практический эффект.

Co-Authored-By: Oz <oz-agent@warp.dev>
```

**scope** — короткий идентификатор группы: `transport`, `p2p/crypto`, `build`, `deps`, etc.

**Правила текста:**
- Нет ASCII-стрелочек (`->` вместо `→`)
- Нет длинных тире (пиши `-`, не `—`)
- Названия классов, методов, файлов — не переводить
- Остальное — по-русски

## Особые случаи

**Если изменений очень много и явной структуры нет:**
Прочитай diff и определи смысловые кластеры по содержанию, а не по файловой структуре.

**Если файл участвует в двух группах:**
Обычно это признак того, что группы нужно объединить или файл разбит неверно.
Предпочти включить файл в ту группу, ради которой он менялся больше всего.

**Если изменение в одном файле касается разных фич:**
Используй `git add -p` для интерактивного выбора патчей внутри файла.

**Если нет смысла делить:**
Для мелких изменений (1-3 файла одного модуля) — один коммит, не делай искусственных
разбивок.

## Проверка после коммитов

После всех коммитов выполни `git log --oneline -N` (где N = число коммитов) и выведи
историю пользователю, чтобы он мог убедиться в правильности порядка и содержания.
